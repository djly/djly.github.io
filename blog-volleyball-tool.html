Volleyball Analytics Tool · August 2026

One data model, four representations

The hard part of this tool was never the framework choice. It was getting vision, game logic, a relational API, and a graph database to agree on what a "rally" is.

The tool takes raw volleyball match video and turns it into structured data: computer vision handles homography and player/ball tracking, game logic classifies actions — serve, pass, set, spike, block, dig — and segments the footage into rallies, and the results land in a Neo4j graph exposed over GraphQL, with an optional Postgres-backed REST API and a frontend for annotation-driven review. This started because I play volleyball and wanted to actually see the patterns in a match, not because I set out to build a data-modeling exercise. It turned into one anyway.

Four layers, one meaning

A Match has many Rallies; each Rally has a server, an optional scorer, a list of participating players, and an ordered list of Events — one per touch. That's a small model. The problem is that it has to exist identically in four places that don't naturally agree on anything:

  • the vision/game-logic pipeline, where a player is just a tracking ID string with no persistent identity;
  • the REST API, backed by Postgres, where everything is an auto-incrementing integer primary key;
  • Neo4j, which can go either way on IDs and needs an explicit link back to the vision layer's track IDs; and
  • GraphQL, which exposes all of the above as opaque string IDs regardless of what's underneath.

Left alone, each layer will happily invent its own shape for "rally," and then the frontend spends its life translating between four dialects that drift further apart every time someone adds a field to one of them.

Writing the model down before writing more code

The fix wasn't a framework — it was a canonical data-model document that every layer has to align to, with rules that are specific enough to catch bugs on their own: a rally's server_id must be a member of its players_involved; a scorer_id, when set, must be too; player lists can't contain duplicates; and when the vision pipeline can't confidently infer who scored, the field is null rather than guessed. That last rule matters more than it looks — a system that's honest about uncertainty is more useful downstream than one that always produces a confident, occasionally wrong answer.

Rally scoring itself is inferred, not detected directly: the game-logic layer looks at the last touch on the side that won the exchange — a kill, or the opposing side's error — and credits that player, falling back to null when the inference isn't reliable enough to commit to.

Product thinking, not just pipeline thinking

The monetization plan shaped the architecture as much as the data model did. Pricing is usage-based — matches processed, plus video minutes priced by resolution, since a 4K match costs noticeably more vision compute than 720p and the pricing should reflect that rather than charging everyone the same flat rate. Video ingestion defaults to the user's own cloud storage — Drive, S3, Dropbox — rather than assuming the platform should host every video by default; hosting is an explicit paid add-on for people who want it, not the default cost center.

The framework is the easy 80%. Getting four systems to agree on what a "rally" means is the fullstack problem.
