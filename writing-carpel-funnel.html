Carpel Funnel · August 2026

The routine is the character

An idle RPG where you never touch combat directly — you program the priorities your character fights by, and a bad routine has to genuinely lose to a good one on identical gear.

Carpel Funnel (working title internally: Idle Exile) is a Path of Exile–inspired mobile idle RPG. The loop is Equip & Build → Program Routine → Deploy → Loot: gear up a character, write the priority list it fights by — "if HP under 30%, use a flask; if a boss is detected, cast this" — send it off to clear content unattended, and come back for the loot. It's still at the design-doc and MVP-spec stage; the interesting work right now is proving the core loop is fun before committing to simulation code.

The constraint that decides everything else

The premise only works if the routine actually matters. If combat resolves as a stat-lookup — good gear wins regardless of what the routine says — the "programming" part of the game is theater. So the server has to genuinely execute player-authored logic, tick by tick, and a well-written routine has to clear meaningfully faster than a starter one on identical gear — by design, as much as a 5x spread in clear speed for the same character.

That's expensive if taken literally: tick-based simulation for every character, all the time, doesn't scale. The resolution is a hybrid model — cheap statistical approximation for bulk offline farming, and full deterministic tick-based simulation (100ms ticks) only when it matters: pinnacle bosses, a player actively spectating, or anything where an approximation would feel unfair. The tick-based runs periodically feed back into the approximation's parameters, so the cheap model stays accurate without ever being asked to carry the content that actually needs fidelity. Server cost ends up bounded by how many players are online watching, not by how many characters exist — and because better routines clear faster, they're also cheaper to simulate than bad ones.

The Codex: progression that isn't a bigger number

The part of the design I'm happiest with has no equivalent in Path of Exile. The routine editor's own vocabulary — conditions like "surrounded" or "boss detected," actions like "kite" or "cast," logic operators like IF/ELSE — isn't available from the start. It's discovered, tiered, and slotted from a personal library called the Codex. A player who hasn't found the "surrounded" condition literally cannot write a routine that reacts to being surrounded, regardless of how good their gear is.

That solves two problems I actually care about. First, idle games struggle to answer "what do I do between gear upgrades" — the Codex gives a second progression axis that's about precision, not bigger numbers: a tier-3 HP-check doesn't heal more, it just lets you set a 1% threshold instead of a fixed 30/50/70. Second, it kills routine copy-paste as a way to skip the game: a top player can publish their boss-killing routine, a newcomer can import it, and it'll show half its rows greyed out until they've earned the same vocabulary. The routine is a blueprint; the Codex is the toolbox, and you can't borrow someone else's.

Server-authoritative, on purpose

Simulation workers are stateless and horizontally scalable, pulling jobs from a queue; Postgres is the source of truth, with routines stored as JSONB specifically so the routine grammar can keep evolving without a schema migration every time a new node type ships. Redis is a queue and cache, not a system of record. Replay logs — the actual combat event stream a player can watch back — live in object storage with a TTL, because nobody needs an infinite archive of maps they cleared six months ago. And the client is deliberately treated as a view layer: it renders results, it never generates them, which closes off most of the obvious cheating surface before it opens.

Two players with identical gear should be able to perform differently — and the difference should be earned, not bought.
